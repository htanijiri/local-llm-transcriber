# 004 Web：音声・動画のアップロード

- 状態：ドラフト
- 依存：003（Web：閲覧／ダウンロード）

## 背景・課題
- 今は、処理したい音声を Drive の監視フォルダに入れるのに、Drive のアプリや Finder を使う必要がある。
- 003 の Web 画面から直接アップロードできれば、外出先のスマホで録った音声などもすぐ処理に回せる。

## ゴール
- Web 画面から音声・動画ファイルを Drive の「音声入力」フォルダにアップロードでき、あとは既存のパイプライン（watch）がそのまま処理する。

## やらないこと
- パイプライン側の変更（Drive for desktop の同期と watch に任せる）。
- 2 チャンネル（`.2ch`）の組のアップロード（002 のエクスポーターが担当）。
- ブラウザ内での音声の変換・圧縮・録音。
- アップロード済みファイルの削除・差し替え。

## 受け入れ条件
- [ ] AC1：一覧画面からファイルを選んで（PC ではドラッグ＆ドロップでも）、「音声入力」フォルダにアップロードできる。複数ファイルを同時に選べる。
- [ ] AC2：受け付ける拡張子はパイプラインの対象（`config.example.toml` の `[watch].extensions` と同じ：`.m4a .mp3 .wav .aiff .mp4 .mov`）に限り、それ以外は選択時に理由を表示して弾く。
- [ ] AC3：ファイルごとに進捗（%）を表示し、完了・失敗がわかる。
- [ ] AC4：1GB 程度の動画でもアップロードでき、通信が一時的に切れても途中から再開できる（Drive の resumable upload を使う）。
- [ ] AC5：同じ名前（拡張子を除いた名前）の会議がすでに「音声入力」「文字起こし」「議事録」のどこかにある場合は、アップロード前に知らせ、別名にする（例：末尾に `_2`）か中止するかを選ばせる。
  （パイプラインは `議事録/<名前>.md` があると処理済みとみなすため、同名のまま上げると処理されずに放置される）
- [ ] AC6：アップロード完了後、一覧にその会議が `処理待ち` として表示される。
- [ ] AC7：アップロード完了後、mac mini の watch が実際に処理し、議事録ができる（Drive for desktop の同期を含めた通し確認）。

## 設計方針
- Drive API v3 の resumable upload（`uploadType=resumable`）でチャンク送信する。親フォルダは 003 で選んだ「音声入力」フォルダ。
- 拡張子の一覧と、名前の衝突判定（003 の「名前の突き合わせ」の規則を再利用）は純粋な関数にしてテストする。
- 拡張子の一覧は Web 側の設定として持つ。パイプライン側の設定と二重管理になるので、CLAUDE.md の「設定キーを変えたら揃える」対象に加える。
- スマホでは、アップロード中に画面を閉じたりアプリを切り替えたりすると中断されうる。中断された場合は再開ボタンで続きから送る（セッション URI を保持する）。

## 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 通常のマルチパートアップロード | × | 大きな動画で失敗しやすく、途中から再開できない |
| resumable upload | ○ | 大きなファイルと不安定な回線に強い |
| 同名なら上書き・自動で別名 | × | 上書きは既存の会議を壊す。自動の別名はユーザーが気づかない |

## 検証方法
- 自動テスト（`node --test`）：拡張子の判定、名前の衝突判定と別名の生成、チャンクの分割計算（AC2, 5）。
- 手動確認（PC・スマホ実機）：複数ファイル、進捗表示、大きな動画、通信の一時切断からの再開（AC1, 3, 4, 6）。
- 通し確認：短い音声をアップロードし、mac mini で議事録ができ、一覧で `完了` になるまで確認（AC7）。

## 未決事項
- OAuth スコープ。最小権限の `drive.file` で、Picker で選んだフォルダ内の既存ファイルの一覧（003）とアップロードの両方ができるかを実際に確認する。できなければ `drive`（フルアクセス）にする。
- 共有された側のアカウント（フォルダの所有者ではない方）から、API 経由でアップロードできるか（フォルダは編集者権限で共有済み）。
- 1 ファイルあたりのサイズ上限を設けるか（Drive の空き容量との兼ね合い）。
