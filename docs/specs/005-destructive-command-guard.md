# 005 破壊的な操作のガード

- 状態：ドラフト
- 依存：—

## 背景・課題
- このプロジェクトで Claude が触る範囲には、取り返しがつきにくいものがある。
  - Google Drive 上の音声・文字起こし・議事録（**2 名で共有しているため、消すと相手の手元からも消える**）
  - Git 管理外の資料（`journal/`、`TODO.md`、`config.toml`、`samples/`）
  - 常駐している watch（launchd）と、その設定
  - 録音アプリ（Kanary）の録音データ
- 権限モードを自動（auto）で使っているため、多くのコマンドが確認なしに実行される。
- 「気をつける」だけでは防げないので、仕組みで止めたい。

## ゴール
- 上の対象に対する破壊的な操作を、実行前に止める。
- 普段の作業（テスト実行、コミット、ファイル編集）は今までどおり止まらない。

## やらないこと
- Claude 以外（自分が手で実行するコマンド、他のアプリ）の操作の制限。
- バックアップの仕組みそのもの（Drive のゴミ箱と履歴に任せる）。
- 権限モードを手動（Manual）に戻すこと。確認の回数が増えて作業が進まなくなるため、自動のまま守りを足す。

## 受け入れ条件
- [ ] AC1：`rm -rf`、`git reset --hard`、`git clean`、`git push --force` は実行されず、拒否される。
- [ ] AC2：Drive の監視フォルダ・文字起こしフォルダ・議事録フォルダ配下を消す／移動する／上書きするコマンドは拒否される（パスは `config.toml` から読む。設定を変えたらガードも自動で追従する）。
- [ ] AC3：`journal/`、`samples/`、`config.toml`、Git 管理外の資料（`TODO.md` など）を削除・上書きするコマンドは拒否される。
- [ ] AC4：`config.toml` は Claude の編集ツールで変更できない（`config.example.toml` は変更できる）。
- [ ] AC5：Kanary の録音を変更するコマンド（`kanary recordings delete` / `import` / `transcribe`）は拒否される。読み取り（`list` / `show` / `status`）はそのまま使える。
- [ ] AC6：launchd の操作（`launchctl`）と `git push` は、実行前に確認を求める（拒否はしない）。
- [ ] AC7：サンドボックスを全プロジェクトで有効にし、作業ディレクトリと一時ディレクトリの外への書き込みが OS レベルで止まる。そのうえで、開発に必要なキャッシュ（uv、Hugging Face、npm 等）への書き込みは許可され、`uv run pytest` や `uv sync` が止まらない。
- [ ] AC8：通常の作業（`uv run pytest`、`uv run ruff`、`git add/commit`、ファイルの編集、`lt` コマンドの実行）は、追加の確認なしに動く。
- [ ] AC9：ガードが働いたことがログに残り、あとで見返せる。

## 設計方針
3 層で守る。1 層目と 2 層目はコマンドの文字列を見るだけなので**回避可能**（`sh -c` 経由、Python スクリプト、絶対パスでの起動など）。回避されても困る部分は 3 層目（サンドボックス）で受け止める。

1. **`permissions` の deny / ask ルール**（`.claude/settings.json`。リポジトリで共有し、公開する。個別のパスはルールに書かず `config.toml` から読むため、公開して困る情報は含まない）
   - `deny`：`Bash(rm -rf:*)`、`Bash(git reset --hard:*)`、`Bash(git clean:*)`、`Bash(git push --force:*)`、`Bash(kanary recordings delete:*)` など。`Edit(config.toml)` も入れる。
   - `ask`：`Bash(launchctl:*)`、`Bash(git push:*)`。
   - deny はサブコマンドや `$(…)` の中まで見て一致する。ただし、同じことを別の書き方（`sh -c "rm …"`、`python -c "shutil.rmtree(…)"`）でやる場合は一致しない。
2. **PreToolUse hook**（`.claude/hooks/guard-destructive.sh`）
   - Bash コマンドの本文を受け取り、`config.toml` から読んだ Drive のパスや、保護対象のディレクトリに対する破壊的な操作（`rm`、`mv`、`>` による上書き、`find -delete`、`truncate` など）を見つけたら拒否する。
   - ルールを1か所のスクリプトにまとめ、拒否した内容をログ（`logs/guard.log`）に残す（AC9）。
   - 判定は「保護パス × 破壊的な動詞」の組み合わせで行い、判断に迷う形（変数展開、`sh -c`）は拒否側に倒す。
3. **サンドボックス**（`~/.claude/settings.json` の `sandbox.enabled`。全プロジェクトを対象にする）
   - macOS の Seatbelt による OS レベルの制限。書き込みは作業ディレクトリと一時ディレクトリに限られるため、Drive のフォルダやホーム直下は、どんな書き方でも書き換えられない。
   - 開発に必要なキャッシュだけ `sandbox.filesystem.allowWrite` で個別に許可する（ツールをサンドボックスから除外するより範囲が狭い）。
   - Drive への書き込みが必要な確認（実データでの `lt run` など）は、サンドボックス外の実行として個別に許可する。
   - `rm` を全面的に拒否しない方針のため、一時ファイルの掃除は今までどおりできる。作業ディレクトリ外の削除はサンドボックスが止める。

## 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 権限モードを手動に戻す | × | 確認の回数が増えすぎて、作業が進まない |
| deny ルールだけ | × | 文字列の一致なので、別の書き方で回避できる。単体では守りきれない |
| PreToolUse hook だけ | × | 同上。ただし deny ルールより柔軟に書ける |
| deny ルール＋hook＋サンドボックス | ○ | 普段は軽い層で早く止め、抜けた分を OS レベルで受け止める |

## 検証方法
- 自動テスト：hook のスクリプトに、拒否すべきコマンドと通すべきコマンドを流して結果を確認する（`bats` は使わず、テスト用のシェルスクリプトか pytest から実行）。ケースは AC1〜5 と AC8 から作る。
- 手動確認：一時的なテスト用フォルダを保護対象に設定し、実際に Claude に削除を依頼して止まることを確認する。
- 手動確認：サンドボックスを有効にした状態で、作業ディレクトリ外への書き込みが失敗することを確認する（AC7）。

## 未決事項
- サンドボックスを有効にすると止まる書き込みの洗い出し（実装時に実行して確認する）。少なくとも次は作業ディレクトリの外に書くため、`sandbox.filesystem.allowWrite` に追加する想定：uv のキャッシュ（`~/.cache/uv`）、Hugging Face のモデルキャッシュ（`~/.cache/huggingface`、mlx-whisper のモデル取得）、npm/npx のキャッシュ（`~/.npm`、Web のデプロイで使う）。
- Drive のフォルダへの書き込みが必要な確認（実データでの `lt run`、watch の動作確認）をどう扱うか。サンドボックス外での実行として都度許可する想定。

（決定済み：ルールは `.claude/settings.json` に置いて共有・公開する。サンドボックスは `~/.claude/settings.json` で全プロジェクトを対象に有効化する。`rm` の全面禁止はしない）
