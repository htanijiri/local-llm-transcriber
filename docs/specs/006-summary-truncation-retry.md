# 006 要約の途中切れの検知と再試行

- 状態：完了
- 依存：000（Ollama 呼び出しを差し替えたテスト、watch の1回分の走査の切り出し）

## 背景・課題
- 要約（Ollama 0.30.10 ＋ qwen2.5:14b）の応答が、文の途中で終わることがある。
  - 同じ文字起こし（約5,600字、単一パス）を6回要約したところ、3回が途中で終わった。3回とも同じ位置（特定の人名を含む段落の書き出し）だった。
  - 途中で終わった回は、完走した回の半分ほどの長さで、見た目は「短めの議事録」に見える。
- 途中で終わった回の応答には、生成の完了を示す情報が入っていない。
  - `done_reason`・`eval_count`・`prompt_eval_count` が無い（Python の `ollama` パッケージ 0.6.2 では `None`）。完走した回は `done_reason` が `"stop"` になる。
  - HTTP ステータスは 200 で、例外も出ない。
- Ollama のサービスログでは、該当箇所でモデルが壊れた UTF-8（マルチバイト文字の途中までのバイト列の直後に ASCII 文字列）を出力し、直後にサーバー側で生成が打ち切られていた。同じ打ち切りは過去の運用中のログにも2回残っていた。
- `transcriber/ollama_client.py` の `generate` は応答の本文を返すだけで、生成が完了したかを確認していない。
  - そのため、途中で終わった議事録がエラーなしで保存される。
  - watch は「議事録のファイルがあれば処理済み」と判定するので、常駐運用では再試行もされず、気づく手がかりがログにも残らない。
- 出力トークン上限（`num_predict`）に達して打ち切られた場合（`done_reason` が `"length"`）も、同じく確認していない。

## ゴール
- 生成が完了しなかった応答を、議事録として保存しない。`summary_dir` の `<stem>.md` は、完了した生成の結果だけになる。
- 完了しなかった場合は、その呼び出しを自動で再試行する。
- 再試行しても完了しなかった場合は、失敗として扱う（例外、ログ、CLI の終了コード）。watch では既存の「失敗時の再試行」に乗る。
- 再試行が起きたこと・失敗したことが、ログから分かる。

## やらないこと
- 打ち切りの原因そのものの解消（Ollama やモデル側の不具合の修正、別の実行エンジンへの切り替え）。発生条件の切り分けは、この仕様の前提にせず、別の調査として進める。原因が分かって発生自体を防げるようになっても、検知は残す。
- 途中までの出力の続きを生成させること（続きから再開）。
- 出力の中身から途中切れを推測すること（文末が句点か、文字数が少なすぎないか、など）。
- すでに保存されている過去の議事録の点検・作り直し。
- 失敗の通知（メール、チャット等）。ログに残すところまで。
- 接続失敗・モデル未取得など、既存の `OllamaError` の扱いの変更。要約の中では再試行せず、今までどおり watch のクールダウン付き再試行に任せる。
- 文字起こし（mlx-whisper）側の変更。

## 受け入れ条件
すべて自動テスト（pytest）で確認する。Ollama は呼び出さず、`ollama` パッケージのクライアントを差し替えて、応答（本文・`done`・`done_reason`）を1回ごとに指定する。
以下で「中断応答」は `done_reason` が無い応答、「上限応答」は `done_reason` が `"length"` の応答を指す。

**完了の判定（`ollama_client.generate`）**
- [x] AC1：`done_reason` が `"stop"` の応答は、今までどおり本文（前後の空白を除いたもの）を返す。
- [x] AC2：中断応答は本文を返さず、「生成が完了しなかった」ことを表す例外になる。例外は `OllamaError` の一種で、`done_reason`（この場合は無し）と、途中までの出力の文字数を持つ。メッセージに途中までの本文は含めない。
- [x] AC3：上限応答も例外になる。AC2 の例外と区別でき、メッセージに `num_predict` の現在値と「上限に達した」ことが含まれる。
- [x] AC4：`done_reason` が `"stop"` 以外の値（`"length"` 以外の未知の値を含む）は、すべて完了していないものとして扱う。

- [x] AC6：単一パスで、`max_attempts` 回（既定3）すべてが中断応答のとき、例外になり、`<stem>.md` は作られない。生成の呼び出しはちょうど `max_attempts` 回。
- [x] AC7：AC6 の状況で、同じ名前の議事録がすでにある場合、その内容は変わらない。

- [x] AC9：接続失敗など既存の `OllamaError` は、要約の中では再試行しない（生成の呼び出しは1回）。

**watch**

- [x] AC17：AC16 の再試行では、文字起こしをやり直さない（文字起こしの呼び出しは、最初の1回だけ）。
- [x] AC18：文字起こしが失敗した場合の再試行は、今までどおり文字起こしからやり直す。

## 設計方針
**完了の判定**
- `ollama_client.generate` で、応答の `done_reason` を確認する。`"stop"` のときだけ本文を返す。
- 判定に使うのは `done_reason` だけにする。`eval_count` の有無や `done` の値は使わない（中断応答で `done` がどう返るかは確認できていないが、判定はそれに依存しない）。
- 完了しなかった場合は、`OllamaError` を継承した例外を送出する。例外は次を持つ。
  - `done_reason`（無い場合は `None`）
  - 途中までの出力の文字数
  - 再試行で直る見込みがあるか（中断は「ある」、上限到達は「ない」）
- 途中までの本文は、例外メッセージにもログにも含めない（ログに会議の内容を残さない）。

**再試行**
- 再試行の単位は、生成の呼び出し1回（単一パスの1回、map の1チャンク、reduce）。`summarize.py` の中の呼び出し箇所で行う。`ollama_client` は判定と例外まで。
- 再試行は、同じプロンプト・同じ設定で、待ち時間を置かずに行う。既定のサンプリングは毎回結果が変わるため、同じ条件でも完走しうる（背景の例では6回中3回が完走）。
- 回数は `[summarize] max_attempts`（1回の生成あたりの合計試行回数、既定3）。
- 上限到達（`"length"`）は再試行しない。対処は設定（`num_predict`）の見直しなので、メッセージで案内する。
- `num_predict` を `[summarize]` の設定キーにして、`generate` に渡す（今は `generate` の既定値 4096 が使われていて、設定からは変えられない）。既定値は変えない。

**保存**
- `summarize_file` は、要約が最後まで成功したときだけ `<stem>.md` を書く（現状も、例外が出れば書き込みに到達しない。この順序を保ち、テストで固定する）。
- 完了しなかった出力は、どこにも保存しない。

**watch との関係**
- 現状の動き：`process_one`（文字起こし→要約）が例外を出すと、失敗回数を記録し、60秒のクールダウンを置いて最大10回まで再試行する。議事録 `<stem>.md` があるファイルは処理済みとして扱う。
- この仕様で変わること：
  - 途中切れが例外になるので、議事録が保存されず、既存の再試行の対象になる（watch の再試行ポリシー自体は変えない）。
  - 要約の中の再試行（すぐに、最大 `max_attempts` 回）が先に働き、それでも失敗した場合だけ watch の再試行（60秒後、最大10回）に進む。
  - watch の再試行は `process_one` を最初からやり直すため、今のままでは要約の失敗のたびに文字起こし（数分かかる）もやり直す。これを避けるため、そのファイルの文字起こしが成功済みなら、再試行では要約だけをやり直す。成功済みかどうかは watch のプロセス内で覚える（再起動後は文字起こしからやり直す。ファイルのサイズが変わった場合も同様）。
  - 上限到達は、再試行しても同じ結果になるので、1回で「諦め」にする。設定を直して watch を再起動すれば、未処理のファイルとして再び処理される。
- `lt run` は再試行の仕組みを持たないので、要約の中の再試行だけが働く。失敗した場合、文字起こしは保存済みなので `lt summarize` でやり直せる。

**ログ**
- 再試行と失敗は、既存の `log` コールバック（watch）と CLI の出力に1行ずつ出す。要約側にも同じ形のコールバックを渡せるようにする。

## 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| `done_reason` が `"stop"` かどうかで判定する | ○ | Ollama が返す完了の印そのもの。中断と上限到達も区別できる |
| 出力の中身で判定する（文末が句点か、文字数が少なすぎないか） | × | 議事録の書式や長さに依存し、誤検知・見逃しの両方が起きる |
| `eval_count` の有無で判定する | × | `done_reason` と同時に欠けるので情報が増えない。判定の根拠は1つに絞る |
| ストリーミングに変えて、最後のチャンクで判定する | × | 非ストリーミングでも同じ情報が取れる。変更が大きくなるだけ |
| 途中までの出力の続きを生成させる | × | 壊れたバイト列の直後から繋ぐことになり、繋ぎ目の品質を確かめる手段がない |
| 再試行を watch だけに任せる（要約の中では再試行しない） | × | 1回の中断で60秒待ち、`lt summarize` / `lt run` では再試行されない |
| 再試行しても失敗したら、保存しない | ○ | 「`<stem>.md` は完了した議事録だけ」を保てる。watch の処理済み判定と Web 画面が、ファイルの有無をそのまま信頼できる。接続失敗など既存の失敗と同じ扱いになる |
| 同じ名前で、冒頭に「不完全」の注記を付けて保存する | × | watch が処理済みと判定し、再試行されなくなる。下流（Web 画面など）が注記を読み分ける必要が出る |
| 別の名前（例：`<stem>.incomplete.md`）で保存する | × | 失敗に気づきやすくはなるが、成功したときに消す処理と、一覧に出さない処理が増える。途中までの議事録を使う場面が想定しにくい |
| map の一部が失敗したら、そのチャンクを抜かして reduce する | × | 会議の一部が抜けた議事録が、完成品として保存される |
| 上限到達（`"length"`）も中断と同じく再試行する | × | 同じ設定なら同じ位置で切れる見込みが高く、時間だけかかる |
| 上限到達（`"length"`）の出力を、注記付きで保存する | × | 末尾が切れていても大半は読めるが、「`<stem>.md` は完了した議事録だけ」が崩れる。設定を直せば完了した議事録が得られる |

## 検証方法
- 自動テスト（pytest）：AC1〜19。
  - `ollama` パッケージのクライアントを差し替え、応答の列（例：中断→`"stop"`）を指定する。応答の形は、実際に観測した中断応答（`done_reason`・`eval_count`・`prompt_eval_count` が無い）に合わせる。
  - watch（AC16〜19）は、000 で切り出す1回分の走査を使い、時刻を差し替えてクールダウンを進める。文字起こしはダミーに差し替えて呼び出し回数を数える。
  - CLI（AC14）は typer のテスト用ランナーで終了コードと出力を確認する。
- スモークテスト／手動確認：
  - `scripts/smoke.sh`（000）が今までどおり通ること（完了した応答の経路が壊れていないこと）。
  - 途中切れは確率的で、公開できる入力では再現手順を用意できないため、実モデルでの再現確認は受け入れ条件にしない。実装後、常駐の watch を再起動し、運用中にログへ再試行の行が出たら、その議事録が文末まで書けていることを目視で確認する。
