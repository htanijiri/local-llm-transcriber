# 003 Web：文字起こし・議事録の閲覧／ダウンロード

- 状態：ドラフト
- 依存：000（検証の土台）

## 背景・課題
- 文字起こしと議事録は Google Drive のフォルダに出力されるが、Drive のアプリでは Markdown がそのまま表示され読みにくく、会議ごとの「音声・文字起こし・議事録」の対応も一覧できない。
- 外出先のスマホや PC など、どの端末からでも URL だけで見られるようにしたい。

## ゴール
- ブラウザで Google アカウントにログインし、Drive 上の会議を一覧し、議事録と文字起こしを読みやすく表示し、ファイルをダウンロードできる。
- 文字起こし・要約のパイプライン（mac mini 側）には一切手を入れない。Web は Drive のフォルダを読むだけで成立させる。

## やらないこと
- アップロード（004 で扱う）。
- 議事録・文字起こしの編集、削除、リネーム。
- LLM を使う機能（質問応答、再要約など）。
- PWA 化（ホーム画面に追加、オフライン対応）。ブラウザで開いて使う。
- 自前のバックエンド（サーバー、DB、Workers）。データは Cloudflare を経由しない。
- 複数ユーザーでの共有・権限管理。

## 受け入れ条件
- [ ] AC1：Google アカウントでログインでき、ログインしていない状態では Drive の情報を一切表示しない。
- [ ] AC2：設定画面で「音声入力」「文字起こし」「議事録」の3フォルダを Google Picker で選べ、選択は端末に保存される（フォルダ名や ID をコードに書かない）。フォルダの所有者ではない（共有されている）アカウントでも、Picker の「共有アイテム」から同じフォルダを選べる。
- [ ] AC2b：フォルダを共有された 2 つ目のアカウントでログインしても、一覧・表示・ダウンロードが同じように動く。
- [ ] AC3：一覧に、会議ごとに 1 行、名前・日時・状態（`処理待ち`＝音声のみ／`要約待ち`＝文字起こしのみ／`完了`＝議事録あり）を新しい順に表示する。音声ファイルと 001 の `.2ch` フォルダの両方を会議として扱う。
- [ ] AC4：会議を名前で絞り込める。
- [ ] AC5：議事録は Markdown を HTML として整形表示する。表示前にサニタイズし、議事録にスクリプトが含まれていても実行されない。
- [ ] AC6：文字起こしを表示でき、001 の話者ラベル形式（`[HH:MM:SS] 自分: …`）の場合は話者ごとに見分けやすく表示する。
- [ ] AC7：議事録（.md）、文字起こし（.txt）、元の音声・動画をダウンロードできる。
- [ ] AC8：PC（Windows / macOS）の Chrome と Android の Chrome で動作する。スマホ幅（360px 程度）でも横スクロールなしに一覧と本文が読める。
- [ ] AC9：Drive のファイルが 100 件を超えても、ページングして全件を一覧に出す。
- [ ] AC10：独自ドメインのサブドメインで Cloudflare Pages から配信され、`deploy.sh` 1 回でデプロイできる。

## 設計方針
- 構成は manga-viewer と同じ、ビルドなしのクライアントのみの Web アプリ。
  - プレーンな HTML/CSS/JS。フレームワーク、バンドラ、npm なし。
  - Google Identity Services でアクセストークンを取得し、ブラウザから Drive REST API v3 を直接呼ぶ。トークンはメモリにのみ保持。
  - フォルダ選択は Google Picker。選んだフォルダ ID は `localStorage` に保存。
  - Cloudflare Pages へは `deploy.sh`（`wrangler pages deploy` の直接アップロード）でデプロイ。
- 置き場所：このリポジトリの `web/`。Python のパイプラインとはコードを共有しない。
- 秘密情報：OAuth クライアント ID と API キーは `web/config.js`（gitignore）に置き、`web/config.example.js` を共有する。
- 会議の組み立て：3 フォルダのファイル一覧を取り、拡張子（`.2ch` はフォルダ名）を除いた名前（パイプラインの `stem` と同じ規則）で突き合わせる。この突き合わせと状態判定は、DOM や API に依存しない純粋な関数に切り出す。
- Markdown の表示：CDN の Markdown パーサーと DOMPurify を使う。
- 利用者は 2 名（フォルダの所有者と、フォルダを共有された家族のアカウント）。OAuth アプリは「テスト」モードで、この 2 つのアカウントをテストユーザーに登録する。第三者はログインできず、仮にログインできても自分の Drive しか見えない。
- 対象ブラウザは PC（Windows / macOS）と Android の Chrome。他のブラウザ向けの対応は入れない。

## 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| mac mini で Web サーバーを動かし Tailscale で接続 | × | 閲覧端末ごとに Tailscale が必要で、URL だけで見られない。mac mini が止まると見られない |
| Cloudflare Workers でバックエンドを持ち、サーバー側で Drive API を呼ぶ | × | トークン管理とサーバーの保守が増える。データが Cloudflare を経由する |
| クライアントのみ（ブラウザ → Drive API 直接） | ○ | manga-viewer で実績がある。サーバーを持たず、データは Google 以外を経由しない |

## 検証方法
- 自動テスト：会議の突き合わせ・状態判定・話者ラベルの解析などの純粋な関数を `node --test` でテストする（npm 不要。Node は導入済み）（AC3, 6）。
- 自動テスト：サニタイズ済みの HTML にスクリプトが残らないこと（AC5）。
- 手動確認（ローカル）：`python3 -m http.server` で起動し、テスト用フォルダで AC1〜4, 7, 9 を確認。
- 手動確認（本番）：デプロイ後、スマホと PC の実機で AC1, 8, 10 を確認。
